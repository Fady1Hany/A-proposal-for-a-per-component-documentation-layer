# Comparison to existing concepts

The four pieces of this proposal all exist in some form. The specific combination does not appear to. This document maps the landscape honestly.

## 1. Project-level context files

### AGENTS.md (2025)
- **What it is:** A markdown file at the repo root giving AI coding agents project-wide instructions, conventions, and behavioral rules. Vendor-neutral, supported by Codex, Cursor, Claude Code, etc.
- **Overlap:** Same broad goal — give the agent context it cannot derive from code alone.
- **Key difference:** AGENTS.md is **one file per repo**, focused on behavioral rules. This proposal is about **one file per component**, focused on navigation and impact **+** an orchestration layer ( can use AGENTS.md as orchestration layer ) for component-aware agent workflows. It is intentionally project-agnostic: it does not document the project itself or encode its architecture or business logic. Instead, it defines how an AI agent identifies the appropriate COMPONENT.md for the requested task and the execution loop it must follow. That loop is executed against the selected COMPONENT.md, which remains the sole source of component-specific knowledge, including constraints, the modification workflow, change_impact, verification steps, and testing guidance. In short, AGENTS.md defines how the agent works, while each COMPONENT.md defines what the agent needs to know.
  
- **Caveat:** The arXiv paper *"Evaluating AGENTS.md"* (Feb 2026) found that context files can *reduce* task success rates compared to no context. This is a warning about design, not a verdict on the concept — but it is the strongest cautionary data point we have.

### `.cursorrules`, `.windsurfrules`
- Vendor-specific equivalents of AGENTS.md. Same granularity gap.

## 2. Auto-generated code graphs

### Aider Repository Map (2023)
- **What it is:** Tree-sitter + PageRank produces a directed graph of symbols and call edges, compressed into the LLM context.
- **Overlap:** Provides exactly the structural information this proposal puts in `depends_on` and `used_by`.
- **Key difference:** Aider's map is **global and auto-generated at query time**. This proposal's structural fields are **per-component and stored on disk**. The mechanism is similar; the consumption model is different — and this proposal adds authored fields (Change impact, Targeted verification) that a graph cannot derive.

### Cursor semantic indexing + `@`-references
- Embeddings plus symbol-level references. Same mechanism as Aider, different UX. Same gap: structural only, no authored intent.

### CodeGraph / Depwire / CodeKnit / Pharaoh / Riftmap (MCP servers, 2025–2026)
- MCP servers that parse the codebase with tree-sitter, build a dependency graph, and expose blast-radius, dependency tracing, function search as tools the agent can call.
- **Overlap:** These give the agent the *content* of the structural fields on demand.
- **Key difference:** They are **runtime tools**, not documentation. They cost context budget on every query. They do not capture authored intent. This proposal is a static artifact that the agent reads once, with the structural half ideally *generated by* one of these tools.

## 3. Change impact analysis (research field)

### Software Change Impact Analysis (Lehnert et al., cited 243+)
- Mature research area. Dependency-graph rewriting, ripple-effect analysis, snapshot evolution.
- **Overlap:** Provides the theoretical basis for the `change_impact` field.
- **Key difference:** Academic techniques, not a documentation format. This proposal borrows the *content* and packages it as a per-component authored field.

### Coderabbit "Security Blast Radius"
- PR-level tool that extends a diff to its likely affected surface.
- **Overlap:** Same idea, narrower scope (PRs, not components) and narrower consumer (security review, not general agent navigation).

## 4. AI-oriented architecture concepts

### AI-Readable Architecture (Shumilov, *Contemporary*, May 2026)
- **The closest conceptual match.** Proposes a new abstraction layer where structural constraints of a software system are made machine-readable for AI-augmented development.
- **Overlap:** Same core argument — documentation should be reorganized around the AI consumer's constraints.
- **Key difference:** Shumilov frames it at the architecture level. This proposal narrows it to a **per-component schema with four specific fields**, and adds the `verified_against` freshness contract.

### AI-Centric Software Architecture (academia.edu, 2026)
- Argues architecture should be designed for AI consumption, not just human consumption. Conceptual, not a format.

### Design-system-as-MCP (Design Systems Collective, 2026)
- Converts design-system components (props, tokens, usage patterns) into machine-readable metadata that AI tools can query.
- **Overlap:** A *domain-specific* version of this idea, applied to UI components. Worth studying as a precedent for what a generator looks like in practice.

## 5. Traditional structural documentation (precursors)

### Architectural Decision Records (ADRs)
- Per-decision records capturing context + consequences.
- **Difference:** Per-decision, not per-component. Missing the explicit dependency and verification fields.

### C4 model, UML, dependency graphs, call graphs
- Visualization and analysis artifacts.
- **Difference:** Human-oriented, not agent-oriented. Not co-located with components.

### Javadoc / Doxygen / Sourcery
- Extract structure from code, produce reference material.
- **Difference:** Reference material for humans, not navigation packets for agents.

## What is genuinely novel in this proposal

Four things, as far as we can tell from the search:

1. **Per-component granularity**, not per-repo.
2. **The four-field schema, especially `targeted_verification`** — most existing work stops at identifying affected code; few specify which verification procedures to execute.
3. **The split between auto-generated and authored fields.** Existing tools do one or the other. This proposal explicitly delegates structural fields to a generator and intent fields to a human, with the `verified_against` field mediating between them.
4. **Framed explicitly as a context-window mitigation.** Most existing work frames itself as "helping the AI understand the codebase." This proposal frames the documentation as existing *because* the AI cannot hold the whole repo in active context.
